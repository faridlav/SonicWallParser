# SonicWallParser: Claude Code Handoff Brief

Read this file first, then `SonicWallParser-project-checklist.md` (the full task list) and `SonicOS-sample-findings.md` (measured facts from real exports). Put all three in the repo under `docs/` on your working branch before you start.

## 1. Goal

Turn SonicWallParser (a .NET 10 CLI that turns SonicWall `.exp` backups into Markdown, PDF and HTML reports) into a reliable analyzer:

1. Correct, version-aware parsing for SonicOS 6.x through 8.x.
2. A **Security Findings** page that surfaces bad configuration and weak points.
3. A **Migration Checklist** page: a printable, platform-neutral list of everything a technician must rebuild if the client moves to another firewall brand (settings plus values, with "collect manually" flags for things the export cannot contain).
4. A better report layout, CLI features, and thorough tests.

Repo: `faridlav/SonicWallParser`. Reviewed baseline: commit `6d516ec`. Work on a new branch (for example `feature/analyzer-v2`). Do not push to `main` directly.

## 2. Decisions already made

- Supported range: SonicOS **6.x to 8.x**. Anything outside the range is rejected by the CLI with a clear message. 8.x is accepted but marked "unverified" because no 8.x sample exists yet.
- **HTML:** findings and migration checklist are pages inside the same single HTML file. **PDF and Markdown:** they are separate output files.
- PDF paper size: **US Letter**, landscape.
- No migration or config conversion to other brands. Only the checklist.
- The dev owner prefers: meaningful commits with good descriptions, thorough tests (unit, integration, end to end), GitHub Actions kept to a minimum (add the test run to the existing release workflow, or at most one small CI workflow), and no em dashes in any prose, docs or reports.

## 3. Hard constraints

- **Never commit real exports or anything derived from them.** The sample `.exp` files contain real client IPs, domains, user names, VPN names, serials and secrets. Keep them outside the repo (they are listed in section 6) and add `*.exp` to `.gitignore`. Test fixtures must be **synthetic** (hand-written or generated), small, and clearly fake (use reserved ranges such as 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 and example.com).
- **Never read, store or print secrets.** Add a hard deny-list in the extractor for secret-bearing keys (PPPoE credentials, user password and TOTP data, RADIUS, LDAP, AD and ClearPass secrets, NTP passwords, VPN keys, admin TOTP data). See `SonicOS-sample-findings.md` section 6 for the list. Add a test proving no secret key ever reaches a model or any report.
- **Do not guess enum mappings.** If a value is not confirmed, show `Unknown(n)` and note it as unverified. See section 5.
- Follow the existing code style (XML doc comments on public members, nullable enabled, small static classes).

## 4. Work plan and order

Do these in order, committing after each logical step. The checklist file has the detailed items and acceptance notes.

**Phase 1: correctness (checklist sections 1 and 2)**
- Fix confirmed bugs: serial number key (`serialNumber`), DHCP keys (`prefs_dhdynstart`, `prefs_dhdynend`, `prefs_dhdynrouter`, `prefs_dhdynsubnetmask`, `prefs_dhdynlease`, `prefs_dhdyndomainname`, `prefs_dhdyndns0` to `dns2`, `prefs_dhdynwins0` and `1`, `prefs_dhdynscopeactive`, `prefs_dhdynbootp`), link speed key (`eth_link_ability`), zone Guest flag, zone IPS on 7.x, UTC timestamps, and Markdown pipe escaping.
- Replace the `IsDefault` boolean with a derived **rule origin** (AutoGenerated, BuiltInDefault, Custom) using the rules in findings section 3. Make every unused-rule check, in every output, use one shared definition that only evaluates Custom rules.
- Remove or fix always-zero fields (NAT hits).
- Add firmware generation detection from `buildNum`, range enforcement (6.x to 8.x), a clear "unsupported version" error, and a loud warning whenever a core section (rules, zones, interfaces, address objects) comes back empty.
- Replace the coarse known-prefix list with tracking of keys actually consumed, so unparsed keys always surface.
- Remove static mutable state from `TableExtractor` and console output from inside the extractor.

**Phase 2: coverage and analysis foundation (checklist sections 3 and 4)**
- Extend models and extractors: rule name, logging, schedule, users, source service, connection limits, bandwidth, GeoIP and botnet flags; VPN name, peer gateway, enabled state (`ipsecSaDisabled`, believed to mean disabled when `on`), IKE version; schedule day masks; WAN addressing mode; management and admin hardening settings; NTP, syslog, SSLVPN global settings; service license counts and expiry.
- Build the name resolver (nested groups), reference graph, unused and duplicate object detection, and a shared report model that all three exporters render from.

**Phase 3: new pages (checklist sections 5 and 6)**
- Security Findings (severity, location, why it matters, suggested fix, links into the main report). Respect the rule origin from Phase 1. Treat hit counts as review evidence only, and state the reset caveat.
- Migration Checklist (grouped by pre-migration, build, cutover, validation; values pre-filled from the export; "collect manually" flags for keys, certificates, passwords, licenses and credentials).

**Phase 4: layout, CLI and polish (checklist sections 7 to 9, 11)**
- Report layout items, Letter-size PDF with bigger fonts, no near-empty pages, cover, table of contents and bookmarks.
- CLI flags (format selection, quiet, naming), JSON export, redaction mode, diff of two exports, batch mode.
- README, supported-versions table, CHANGELOG.

**Throughout (checklist section 10):** tests alongside each change.

## 5. Open questions (do not guess; use the defaults)

These need confirmation from the SonicOS UI. Until confirmed, use the stated default and mark it unverified:

1. Policy action value `0`: probably **Deny**, currently labeled Discard in code. Default: label `0` as "Deny (0)" and flag as unverified. Allow is `2`; value `1` has never been seen.
2. The IKEv2 VPN on the TZ 470 sample (exchange `3`, encryption `251`, authentication `6`, DH `3`): do not map. Show `Unknown(n)` with the raw value.
3. Default site-to-site values seen in all samples (exchange `2`, DH `1`, encryption `3`, authentication `3`): keep existing labels but flag as unverified.
4. Zone IPS on 7.x: show "unknown" rather than "off" until the source is confirmed.

Ask the dev owner to confirm from the UI, then update the tables and remove the flags.

## 6. Local sample files (not in the repo)

The dev owner has these on their machine. Keep them out of git and reference them only by local path when running manual checks:

- TZ 400, SonicOS 6.5.4.15-117n (one export; the second upload was an identical copy)
- TZ 370, SonicOS 7.1.2-7019-R6288
- TZ 470, SonicOS 7.3.2-7010-R9118

Use them for local verification only: run the CLI on each, check the section counts, and spot-check values against the SonicOS UI. Compare report output before and after your changes. Build the synthetic fixtures by hand to mirror their key structure (see findings sections 1 and 4 for the shape), never by copying or lightly editing them.

Useful facts measured from them (details in the findings file): the core indexed families are the same across 6.5 to 7.3; 7.x adds many rule fields (`policyNg*`, SAML); service group IP types differ (`0` on 6.x, `170` or `171` on 7.x); unassigned interfaces have an empty zone.

## 7. Testing requirements

- **Unit:** every extractor, every enum mapping, rule-origin classification, the resolver, each finding check, the secret deny-list, version detection and range enforcement.
- **Integration:** synthetic fixture to model to each report format, for at least one 6.x fixture and one 7.x fixture.
- **End to end:** run the real CLI on fixtures and assert exit codes, produced files and key content (including the findings and migration outputs, and that unsupported versions fail cleanly).
- **Golden files** for report output so layout regressions are caught.
- Negative cases: corrupt, empty, huge, unsupported-version and CLI-text files.
- Add the test run to the existing release workflow instead of a new workflow if possible.

## 8. Definition of done

- Build and all tests pass locally with `dotnet build` and `dotnet test`.
- CLI run on each real sample produces non-empty, plausible output for every supported section, with no secrets in any report, and no new empty-section warnings that are not true.
- The unused-rule count is identical in every output, and built-in default rules are never listed as cleanup candidates.
- Findings and migration pages appear in HTML (inside the file) and as separate files for PDF and Markdown.
- README documents supported versions, new flags and outputs, and the anonymization guidance.
- Everything unconfirmed is clearly marked unverified in code comments and the report.
- Work is on a feature branch with meaningful commits and a PR description summarizing what changed, what is unverified, and what the dev owner still needs to confirm.
